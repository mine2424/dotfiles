# フェーズ3: 自動レビューと差し戻し
実装が報告されたら、実装者と別の担当に即レビューを依頼する(全文ではなく差分と該当節を渡す)。
- 観点: 受け入れ条件の充足と抜け/AGENTS.md違反(§4依存方向、§10、§14)/認可・テナント分離・秘密/不明の副作用/所有範囲の逸脱/不要な範囲拡大と低価値テスト/検証の不足。
- 出力: 重大度順の表(ファイル:行/問題/根拠)。問題なしなら「指摘なし」と確認した範囲。推測は「未確認」と明記する。
- 重大・中の指摘は実装者へ自動で差し戻し、直ったら再レビューする。それでも残る指摘は判断キューに入れる。
- 認可・APIルート登録を変えたIssueは、`RUN_AUTHZ_MATRIX=1 npx vitest run authz-matrix`を実行する。

# フェーズ4: 報告
- ラウンドごとに表だけで報告: Issue/状態(実装中・レビュー中・差し戻し・完了候補)/branchと最新commit/検証結果/未確認範囲/次の投入。決定ログの表も付ける。
- 判断キューには「判断の方針」の【私に聞く】だけを入れる。溜めておき、(a)ブロックされた作業が3件以上になった、(b)実行枠が空いて投入できる作業がない、(c)私が聞いたとき、のいずれかで、1回にまとめて質問する。質問は、背景・選択肢・推奨・止まっているIssueを書き、最大でも一度に5件にまとめる。
- 設計判断は聞かずに採用し、決定ログとして報告に載せる。私が決定ログを見て覆した場合は、影響するIssueだけをやり直す。
- 私がPR化を指示したら、Issueごとに別PRにする。説明に「何を・なぜ・関連Issue/FR/TC・設計判断・テスト計画・未確認範囲」を書く。
- ProjectのStatusとIssueの更新は私が指示するまでしない。完了候補は、受け入れ・レビューがそろったものだけを挙げる。
- 1つの関心事が終わるたびに、`.claude/handoff/<日付>-<題>.md`(gitの対象外)へ「目的/決定/変更したファイル/未完了/次の一手」だけを書き、/clearを勧める。
