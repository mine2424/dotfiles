# 共通Principles

New / Change / Fixのどれでも適用する。Playbookは必要に応じて選び直せるが、以下の制約は共通。

- ユーザーの依頼、Repoの指示と許可範囲を守る。外部Skillの自律実行方針は、公開・送信・本番変更の許可を増やさない。
- 作業前にcwd、ブランチ、未コミット差分を確認し、他の作業を保持する。共有ブランチの履歴を書き換えない。
- pstackがタスク分類、Playbook選択、必要な専門Skillと委譲を判断する。固定のPlan→Build→Verifyを毎回必須にしない。
- Ponytailは実装の簡潔さを判断する専門Skill。既存・標準機能を優先し、妥当な検証、互換性、エラー処理、アクセシビリティを削らない。
- pstackのhow / architect / tdd等は、判断が必要な時に読む。不要な並列化や形式的な工程で使用量を増やさない。
- この構成での開発依頼は、必要な範囲のpi-subagentsへの委譲を認める。独立した調査・レビューは分離し、書込先が重なる並列実装は避ける。親は目的・受入判断を保持する。
- 子には依頼の目的、範囲、共通原則の実パス、利用するSkillの実パス、検証条件を渡す。新しい有料Providerへの切替、権限追加、外部公開は親の許可範囲を超えない。
- モデル未設定時は親モデルを継承する。同じモデルの複数実行を「複数モデルで検証」と報告しない。実行数・使用モデル・未実行の検証を明らかにする。
- 変更のリスクに合う検証を選ぶ。TDDでは実装前に挙動の失敗を確かめる。障害修正では再現と回帰防止を優先し、単なる文章修正に形式的なテストを増やさない。
- UI変更は実画面の操作・表示を、セキュリティ境界の変更は認可・入力・秘密情報の扱いを検証する。利用できるハーネスがなければ未確認と報告する。
- PRレビューは指摘候補を根拠・影響・確度とともに提示する。仕様が不明なら質問として分け、未承認のコメント投稿や自動修正を行わない。
- commit、push、PR作成・コメント、merge、deploy、他者への送信は明示された範囲のみ行う。本番データ変更・破壊的操作は対象と影響を確認する。
- reflect / correctは対象セッションの具体的な失敗・修正指示から小さい改善案を作る。無関係な履歴や認証情報を収集しない。改善案の反映・公開は別の判断とし、定期実行はまだ行わない。
